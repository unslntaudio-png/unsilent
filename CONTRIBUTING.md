# Contributing

## One task, one owner

Describe the intended outcome and acceptance criteria in the task tracker before starting substantial work. Use one accountable owner and one branch per task. Include the task reference in the branch or pull request where appropriate; do not copy confidential task details into public code discussions.

## Working with coding assistants

Give each assistant a bounded brief: goal, relevant files, constraints, expected output and checks. Avoid concurrent edits to the same files. The return summary should explain changes, verification, unresolved questions and the next action. Treat suggestions as proposals until reviewed.

## Review and completion

Open a pull request against the default branch. Explain the problem and resulting behavior, list meaningful checks, and include screenshots when the interface changes. Keep unrelated changes separate. A task is complete when acceptance criteria are met and the reviewed result is linked in the task tracker.

## Repository contents

Store source code and technical documentation here. Keep credentials, personal data, contracts, invoices, unreleased audio, stems and private business documents outside this repository. Use environment variables or an approved secret store for credentials and keep example values fictitious.

## Local work

Use a local code checkout and Git for version history. Business files belong in their designated file storage. Follow any project-specific setup and testing instructions already present in the repository.
